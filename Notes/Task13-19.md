# GitHub Actions Lab — Tasks 13 → 19

## Task 13 — Workflow Permissions

### Purpose
Understand the `permissions:` block and control what the `GITHUB_TOKEN` can access.

Example:

```yaml
permissions:
  contents: read
  issues: write
```

We tested:

- `contents: read`
- `issues: write`
- `permissions: {}` / no permissions
- Attempting operations against the GitHub API.

### Important lesson

The presence of:

```yaml
${{ github.token }}
```

only tells us that a token exists.

It **doesn't mean the token has permission to perform every operation**.

The actual permissions are controlled by the `permissions:` block.

For example:

```yaml
permissions:
  contents: read
```

allows read access to repository contents, but doesn't grant permission to create issues.

We also confirmed that permission names must be the GitHub-supported permission names — for example, `issues`, not `pull_requests`.

# Task 14 — GitHub Issues

### Purpose
Understand what Issues are used for.

We created a test issue and later closed it.

Issues can be used for things such as:

- Bugs
- Feature requests
- Tasks
- Improvements
- Questions
- General work tracking

### Important distinction

An Issue can become a **Project item** and can then participate in a project backlog/sprint workflow.

Conceptually:

```text
Issue
  ↓
Project item
  ↓
Backlog
  ↓
Sprint / active work
```

The Issue remains associated with the Project item rather than disappearing when it enters the project.

We also discussed using GitHub Actions to **automatically create an Issue when something happens**, such as a pipeline failure.

That automatic creation would be implemented **inside a workflow**, not as a repository setting.

# Task 15 — Pull Request Workflow Events

We created a PR CI workflow to understand PR-related events.

Example:

```yaml
name: PR CI

on:
  pull_request:

jobs:
  pre-check:
    runs-on: ubuntu-latest

    steps:
      - name: Show PR Information
        run: |
          echo "PR Number: ${{ github.event.pull_request.number }}"
          echo "Source Branch: ${{ github.head_ref }}"
          echo "Target Branch: ${{ github.base_ref }}"
          echo "Event: ${{ github.event_name }}"
```

### Information we extracted

```text
github.event.pull_request.number
```

→ PR number

```text
github.head_ref
```

→ source branch

```text
github.base_ref
```

→ target branch

```text
github.event_name
```

→ event that triggered the workflow

### PR events we experimented with

- PR opened

- PR merging

An important observation was that **closing a PR without merging doesn't represent a merge event**.

# Task 16 — Required Status Checks

We created a deliberately failing workflow:

```yaml
name: PR Fail CI

on:
  workflow_dispatch:

jobs:
  pre-check:
    runs-on: ubuntu-latest

    steps:
      - name: PR check fail
        run: |
          echo "Running PR CI"
          exit 1
```

The purpose was to create a failed check and investigate whether GitHub would prevent merging.

### Key lesson

A **failed workflow/check does not automatically block a PR merge**.

You need repository rules/rulesets configured to make that check a **required status check**.

We initially had trouble finding the check because the workflow/check and the protected `main` branch needed to line up correctly.

Eventually we tested this with a collaborator account and confirmed:

```text
Required check fails
        ↓
Collaborator attempts merge
        ↓
🚫 Merge blocked
```

Your own account was configured as a bypass actor, so your account could bypass the restriction.

# Task 17 — CODEOWNERS

### Purpose
Understand how GitHub identifies who owns particular files.

We created:

```text
.github/CODEOWNERS
```

and initially used a pattern covering workflows.

For example:

```text
.github/workflows/* @tarun-bansal-tester
```

### What happened

When a PR modified a matching workflow file, GitHub automatically requested the CODEOWNER as a reviewer.

We observed:

> `simple-tech-with-tarun requested your review on this pull request.`

So:

```text
PR changes owned file
        ↓
CODEOWNERS pattern matches
        ↓
Code owner identified
        ↓
Owner requested as reviewer
```

### Important distinction

CODEOWNERS does **not** mean:

> "This person is the assignee of the PR."

Instead:

> "This person/team owns these files and should review changes to them."

# Task 18 — Require Review From Code Owners

We already had a ruleset requiring:

> 1 approving review

Then we enabled:

> **Require review from Code Owners**

### Important distinction

These are two different concepts:

```text
Require 1 approving review
        ↓
Someone eligible must approve
```

versus:

```text
Require review from Code Owners
        ↓
The relevant CODEOWNER must approve
```

Because our ruleset already required one review, the PR was already blocked without an approval.

The visible difference after enabling CODEOWNERS was that the appropriate owner was automatically requested.

We also tested a more specific CODEOWNERS pattern:

```text
.github/workflows/pr-ci.yml @tarun-bansal-tester
```

Then we modified:

```text
.github/workflows/permissions.yml
```

The collaborator was **not automatically requested as the CODEOWNER**, because:

```text
permissions.yml
        ≠
pr-ci.yml
```

This demonstrated that CODEOWNERS patterns determine **exactly which files trigger ownership**.

# Task 19 — Workflow Concurrency

### Purpose
Understand how GitHub controls multiple simultaneous workflow runs.

We created:

```text
.github/workflows/concurrency-lab.yml
```

with a deliberately slow step:

```yaml
- name: Start
  run: |
    echo "Starting..."
    sleep 30
```

### Baseline — no concurrency

We started two runs close together.

Observed:

```text
Run #1 → Running
Run #2 → Running
```

Both ran at the same time.

Therefore:

> Without a concurrency configuration, GitHub can run multiple instances of the workflow simultaneously.

---

## Task 19A — `cancel-in-progress: true`

We added:

```yaml
concurrency:
  group: concurrency-lab
  cancel-in-progress: true
```

Then started two runs.

Observed:

```text
Run #1 → Running
Run #2 → Pending
Run #1 → Cancelled
Run #2 → Running
Run #2 → Completed
```

### Meaning

```yaml
group: concurrency-lab
```

puts the runs into the same concurrency group.

```yaml
cancel-in-progress: true
```

means:

> When a newer run starts, cancel the currently running run in the same group.

This is useful for CI when a newer commit makes an older CI run obsolete.

Example:

```text
Commit A
   ↓
CI running

Commit B
   ↓
new CI run
   ↓
Cancel CI for A
   ↓
Run CI for B
```

# Task 19B — `cancel-in-progress: false`

We then changed:

```yaml
concurrency:
  group: concurrency-lab
  cancel-in-progress: false
```

We started two runs again.

Expected/observed behavior:

```text
Run #1 → Running
Run #2 → Pending
Run #1 → Completed
Run #2 → Running
Run #2 → Completed
```

### Meaning

With `false`:

> Don't cancel the currently running workflow. Let it finish and allow the newer run to wait.

So the difference is:

| Setting | Older run | Newer run |
|---|---|---|
| `true` | Cancelled | Runs |
| `false` | Finishes | Waits, then runs |

### Practical CI interpretation

```text
cancel-in-progress: true
→ "Newer run replaces the old one."

cancel-in-progress: false
→ "Finish the old run, then process the new one."
```
