# Task 20 — Security

### Purpose

Understand practical security controls for GitHub Actions workflows, repository dependencies, secrets, and third-party Actions.

We approached security as a practical lab rather than a single feature.

---

## 20A — `GITHUB_TOKEN` Permissions

We verified that a workflow receives a `GITHUB_TOKEN`, but the existence of the token does **not** mean it has unrestricted permissions.

We used:

```yaml
permissions:
  contents: read
```

### Important lesson

The effective permissions of `GITHUB_TOKEN` are controlled by the workflow/repository permission configuration.

For example:

```yaml
permissions:
  contents: read
```

allows repository content read access but does not grant arbitrary write capabilities.

This reinforced the principle:

> Give workflows the minimum permissions they actually need.

---

## 20B — Repository Secrets

We created a **repository secret** and attempted to consume it from a workflow.

### Important lesson

Secrets can be supplied to workflows without placing sensitive values directly in the workflow YAML.

A secret should not be deliberately printed to logs.

Conceptually:

```text
Repository Secret
       ↓
GitHub Actions
       ↓
Workflow step
       ↓
Use secret
```

The workflow should consume the secret only where required.

---

## 20C — `pull_request` vs `pull_request_target`

We investigated why a security-related workflow behaved differently depending on its trigger.

For a PR workflow we observed:

```text
Event: pull_request
Ref: refs/pull/38/merge
```

For the target-based workflow we observed:

```text
Event: pull_request_target
Ref: refs/heads/main
```

### Important lesson

`pull_request` and `pull_request_target` do **not** execute with the same repository/ref context.

`pull_request_target` runs in the context of the base repository, which makes it useful for certain repository-level operations, but also means it requires particular care when processing untrusted PR input/code.

---

## 20D — Dependabot

We investigated repository dependency security.

Initially, Dependabot alerts were disabled.

We enabled the relevant security features, including:

- Dependabot alerts
- Dependabot security updates

No vulnerability alerts appeared afterward.

### Important lesson

An empty Dependabot alert list does **not** mean Dependabot isn't working.

It means there were no currently detected vulnerabilities matching the repository's dependencies.

We did not introduce an intentionally vulnerable dependency just to manufacture an alert.

---

## 20E — Third-Party GitHub Action Pinning

We investigated the security implications of:

```yaml
uses: actions/checkout@v4
```

and learned that `v4` is a **Git reference/tag**.

It is not GitHub Actions interpreting semantic-version ranges.

For example:

```text
v4
v4.4.0
```

are references maintained by the Action's repository.

We verified:

```text
actions/checkout

v4
→ 11d5960a326750d5838078e36cf38b85af677262

v4.4.0
→ 11d5960a326750d5838078e36cf38b85af677262
```

This happened because the maintainer had both tags pointing to that commit.

### Immutable SHA pinning

We then changed:

```yaml
uses: actions/checkout@v4
```

to:

```yaml
uses: actions/checkout@11d5960a326750d5838078e36cf38b85af677262
```

The workflow executed successfully.

### Important lesson

A full commit SHA pins the Action to an **exact immutable Git commit**.

Conceptually:

```text
@v4
 ↓
Git tag
 ↓
commit selected by maintainer

@<full SHA>
 ↓
exact Git commit
```

Therefore SHA pinning reduces the risk of a moving tag unexpectedly changing the code executed by the workflow.

---

## 20F — SHA vs `GITHUB_SHA`

We also distinguished two different concepts that are easy to confuse.

### `GITHUB_SHA`

```text
GITHUB_SHA
```

is the commit associated with the workflow run/repository event.

### Action SHA

The SHA used in:

```yaml
uses: actions/checkout@<SHA>
```

is the exact commit of the **Action repository** being executed.

They are therefore unrelated SHAs.

For example:

```text
Workflow repository commit
        ↓
GITHUB_SHA

actions/checkout repository commit
        ↓
Action SHA
```

### Final security principle

For production-oriented workflows:

```text
Least-privilege permissions
        +
Secure secrets
        +
Careful PR trigger selection
        +
Dependency security
        +
Pinned third-party Actions
```

form the practical security baseline we established in this lab.

# Task 21 — CI/CD Pipeline

### Purpose

Combine the GitHub Actions concepts learned throughout the lab into a realistic CI/CD pipeline.

Rather than creating isolated demonstrations, we built one pipeline incrementally and actually executed it.

---

## 21A — Pipeline Structure

The final pipeline consisted of:

```text
Validate
   ↓
 Test
   ↓
 Build
   ↓
Upload Artifact
   ↓
 Package
   ↓
Deploy
```

Job dependencies were implemented using `needs`.

For example:

```yaml
test:
  needs: validate
```

and:

```yaml
build:
  needs: test
```

This created an explicit execution order.

---

## 21B — Validate

The validation job checked repository/workflow context:

```text
Repository: simple-tech-with-tarun/github-actions-lab
Commit: <GITHUB_SHA>
Ref: <GITHUB_REF>
Validation passed
```

This reused concepts learned earlier around GitHub context and runner information.

---

## 21C — Test

We created a simulated test stage:

```text
Running tests...
Tests passed
```

The purpose was to establish the CI stage before the build.

The job depended on successful validation.

---

## 21D — Build

The build job created a simulated application output:

```text
build/
└── build-info.txt
```

with:

```text
CI/CD Pipeline Build
```

This gave us a tangible build output that could be passed to later jobs.

---

## 21E — Artifacts

We uploaded the build output using:

```yaml
uses: actions/upload-artifact@<SHA>
```

with the artifact name:

```text
application-build
```

The artifact contained:

```text
build/build-info.txt
```

### Important lesson

Each GitHub Actions job can run on a separate/fresh runner.

Therefore:

```text
Build job filesystem
        ≠
Package job filesystem
```

The artifact provides the bridge:

```text
Build
 ↓
upload-artifact
 ↓
GitHub artifact storage
 ↓
download-artifact
 ↓
Package
```

---

## 21F — Package

The Package job ran on its own runner and downloaded:

```text
application-build
```

using:

```yaml
uses: actions/download-artifact@<SHA>
```

We verified that the downloaded artifact contained:

```text
CI/CD Pipeline Build
```

This demonstrated that the build output successfully crossed the job boundary.

---

## 21G — Conditional Deployment

We did not want every PR/feature branch to deploy.

Therefore, the deployment job was restricted using:

```yaml
if: github.ref == 'refs/heads/main'
```

This created two behaviors.

### Feature branch / PR

```text
Validate   ✅
Test       ✅
Build      ✅
Package    ✅
Deploy     ⏭️ skipped
```

### Main branch

```text
Validate   ✅
Test       ✅
Build      ✅
Package    ✅
Deploy     ✅ eligible
```

### Important lesson

The same workflow can provide CI for branches/PRs while reserving deployment for `main`.

---

## 21H — Production Environment

We created a GitHub Environment:

```text
production
```

and attached it to the deployment job:

```yaml
environment: production
```

We then configured a **required reviewer/approval** for that environment.

This turned the deployment from a simple workflow step into a protected deployment.

---

## 21I — Production Approval

After the pipeline was merged to `main`, the deployment became eligible.

The deployment reached the `production` environment and waited for approval.

The resulting flow was:

```text
main
 ↓
CI
 ↓
Deploy job
 ↓
production environment
 ↓
⏸ Required approval
 ↓
Approval
 ↓
Deployment
 ↓
Successful
```

We actually completed this successfully.

---

## 21J — Action SHA Pinning in the Final Pipeline

Before finalizing the pipeline, we pinned all external Actions used by it.

### Checkout

```text
11d5960a326750d5838078e36cf38b85af677262
```

### Upload artifact

```text
ea165f8d65b6e75b540449e92b4886f43607fa02
```

### Download artifact

```text
d3f86a106a0bac45b974a628896c90dbdf5c8093
```

So the final pipeline did not rely on moving `v4` tags for these Actions.
